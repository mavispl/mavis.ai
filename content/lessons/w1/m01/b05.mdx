A model produces tokens. Everything else — a validated object, a database query, a file written to disk — is a matter of how you constrain and interpret those tokens. There are four distinct mechanisms, and most brittle AI integrations come from reaching for the wrong one.

<Plainly>
Four ways to get something usable out of a model:

1. **Ask it to write something**, and read the prose.
2. **Ask it to fill in a form** whose shape you defined, and get back a validated object.
3. **Give it a list of buttons it may press**, and when it presses one, your code runs.
4. **Let the provider give it buttons** that they run on their own machines.

They look similar from outside and behave very differently when things go wrong. The difference between a demo and a system is usually just picking the right one.
</Plainly>

## 1. Text generation

The default. Useful when a human is the consumer, and dangerous the moment a program is.

The trap is not that free text is bad — it is that free text *usually* parses. You write a regex against the response, it works on twenty examples, you ship. Then the model prefixes its answer with "Certainly! Here's the JSON you requested:" on one input in fifty, and your parser fails. The failures are rare enough to survive review and frequent enough to matter in production, and they cluster on unusual inputs — exactly where you least want them.

**If a program consumes the output, do not use free text.** Use the next mechanism.

## 2. Structured outputs

<Term slug="structured-output">Structured outputs</Term> constrain generation against a schema you supply, so the response is a valid instance rather than something that resembles one. The distinction is enforcement: a prompt asking for JSON is a request; a schema constraint is a guarantee about shape.

This is the right choice for extraction, classification, and any handoff into typed code. The design mistakes are consistent:

- **Schemas that are too permissive.** `{"result": "string"}` gives you a validated blob with no structure. Push the actual shape into the schema — enums for closed sets, arrays for repeats, nested objects for relationships.
- **Fields with no way to say "absent".** If the source document does not contain a date, the model must produce *something* for a required `date` field. It will produce a plausible one. Make it optional, or include an explicit `not_found` variant, and you convert an invented value into a correct one.

<Callout tone="key">
Schema design is where you decide how the model fails. A permissive schema fails as bad data flowing silently into your system; a precise schema with explicit absence variants fails as a value that says "I did not find this". You get to choose which.
</Callout>

## 3. Function calling

<Term slug="function-calling">Function calling</Term> inverts the flow. Instead of the model producing an answer, it produces a *request* — a structured block naming a tool and its arguments. Your harness executes it and returns the result as a <Term slug="tool-result">tool result</Term>, and the model continues with that in context.

The mechanics were covered in the first lesson. What matters here is design.

**The description is a prompt, not documentation.** It is the only thing telling the model when to reach for this tool. Written like API reference — "Queries the user table" — it gets used at the wrong times or not at all. Written like instruction — "Look up a user's subscription status by email. Use this before answering any billing question. Returns null if no account exists." — it gets used correctly. The most common cause of "the agent ignored the tool" is a description written for a human reader.

**Granularity is a real tradeoff.** Narrow tools (`get_user_email`, `get_user_plan`, `get_user_created_at`) are safe and unambiguous, and they burn input tokens on every request forever. One broad tool (`query_users`) is cheap in context and hands the model more authority than you may want. Both are defensible; drifting into forty narrow tools without deciding is not.

**Results are context, so their size is a cost.** A tool returning 4,000 lines of JSON has technically succeeded and practically failed: it consumed the window and left the model searching. Return what is needed, paginate, and prefer a summary with a follow-up tool over a dump.

<ForEngineers>
Details that separate working integrations from flaky ones:

**Parallel calls.** One assistant message can carry several `tool_use` blocks. Execute them concurrently and return **all** `tool_result` blocks in a *single* user message. Splitting them across messages teaches the model, within that conversation, to stop batching — and you lose the concurrency for the rest of the session.

**Errors are results.** A failed tool returns a `tool_result` with `is_error: true` and a message the model can act on. Dropping the block leaves an unresolved call and usually triggers a retry loop. A useful error message ("file not found: src/idnex.ts — did you mean src/index.ts?") often recovers in one turn where a stack trace does not.

**Strict schemas.** Where available, a strict mode guarantees arguments validate exactly — worth enabling for any tool with side effects, so you are validating at the boundary rather than defensively inside the handler.

**Silent non-calls.** If the model writes the *description* of a call as prose instead of emitting a block, the turn succeeds, nothing runs, and no error surfaces. In an agentic loop that prose then pollutes later turns. Always branch on `stop_reason` and look for an actual `tool_use` block rather than trusting the text.
</ForEngineers>

## 4. Native (server-side) tools

Some capabilities are provided by the model vendor and run on their infrastructure: web search, web fetch, code execution. You declare them; results arrive in the same response without a round trip to your code.

It is worth separating three things people collapse into "tools". **Custom tools** are functions you write and execute. **External tools** are third-party systems reached over a protocol — a database, a ticketing system, an MCP server — which are still executed by your harness, but whose behaviour and availability you do not control. **Native tools** are executed by the provider. The security question differs for each: for custom tools you audit your own code, for external tools you are extending trust to another system's output, and for native tools you are extending it to the provider.

The tradeoffs are real and go both ways. You get no execution loop to write and no infrastructure to run. You also give up control over what is fetched and executed, and you take on a dependency on the provider's implementation. And the pricing model is different: <Term slug="native-tool">native tools</Term> commonly bill *outside* the token model — a per-search charge, or container-hours for code execution — which means a cost model built only from input and output rates can be materially wrong for a tool-heavy agent.

## Choosing

| If the consumer is… | Use | Because |
|---|---|---|
| a human reading it | text generation | shape does not need enforcing |
| a program, one shot | structured outputs | the schema is the contract |
| a program, needing real data or effects | function calling | the model requests, you execute and stay in control |
| a program, and the capability is generic | native tools | no infrastructure, at the price of control |

<ForLeads>
**Free text into a program is technical debt with a variable interest rate.** It works in the demo, passes review, and fails on a fraction of production inputs — reported as flakiness rather than as a design error. When someone says the AI feature is "mostly reliable", this is very often the cause, and it is cheap to fix early and annoying to fix late.

**Tool authority is the security surface.** The model has no permissions of its own; every tool you expose is a grant. The review question for any new tool is not "does it work" but "what can this do if the model is persuaded by something it read". That is a normal permissions review, not a novel discipline.

**Native tools trade control for speed of delivery.** Fine for generic capability, worth thinking twice about where the fetched content or executed code sits inside your trust boundary — and worth modelling separately in the budget, since they do not bill like tokens.
</ForLeads>

<Callout tone="danger" title="Don't let a tool result reach an interpreter unvalidated">
Tool results are untrusted input with no privilege marker in the context window. A web page, an issue comment, or a dependency's README fetched by a tool sits alongside your instructions. If that path leads to a shell, an <code>eval</code>, a SQL string, or a template renderer, embedded instructions execute with your process's authority. Parse into a typed structure, allowlist operations, sandbox anything untrusted.
</Callout>

These four mechanisms are the whole interface. Everything in the rest of the course — skills, subagents, multi-agent systems, autonomous pipelines — is built by composing them, and every one of those compositions inherits the failure modes of the mechanism underneath.
