A generative model does exactly one thing: given a sequence of tokens, it produces a probability distribution over what comes next. It has no memory between calls, no access to your filesystem, no ability to run anything. Every capability you associate with "an AI that can do things" — reading your repository, calling an API, remembering yesterday's conversation, working through a task over twenty steps — belongs to the **program wrapped around the model**, not to the model.

That program is called a <Term slug="harness">harness</Term>, and understanding where the boundary sits is the single most useful thing in this course. Almost every confusing behaviour, every surprising cost, and every security incident in AI-assisted engineering lives at that boundary.

<Plainly>
Picture a very well-read person locked in a room with no windows, no phone, and no memory of yesterday. You can slide notes under the door, and they slide notes back. They can write beautifully about almost anything — but they cannot look anything up, cannot check whether what they wrote is true, and will not remember this conversation tomorrow.

The harness is the person standing outside the door: reading the notes, noticing when one says "please look up X", actually looking up X, and sliding the answer back in. From the outside it looks like the person in the room has internet access. They don't. The runner does.
</Plainly>

## The model's actual interface

Strip away every product surface and the interface is this: you send a list of messages, you get back a <Term slug="completion">completion</Term>. Stateless. Send the same input twice and nothing carries over from the first call — if the model appears to remember your last message, it is because the harness sent the entire conversation again.

This has a consequence people find surprising: **a long conversation is not cheaper than a short one.** Every turn resends everything before it. What feels like an ongoing dialogue is a series of independent calls, each one larger than the last.

## What the harness adds

A harness is responsible for everything the model cannot do:

**Assembling context.** Deciding what goes into the request — system instructions, conversation history, file contents, retrieved documents, tool definitions. This is the harness's most consequential job, and the rest of Week 1 is largely about doing it well.

**Executing tools.** The model cannot call anything. What it can do is emit a structured request: *"I would like to call `read_file` with `{path: 'src/index.ts'}`."* The harness matches that against a real function, runs it, and appends the result as another message. Then it calls the model again with the longer conversation.

**Running the loop.** The model produces one response. Everything multi-step — "explore the codebase, find the bug, fix it, run the tests" — is the harness calling the model repeatedly, feeding each result back in, and deciding when to stop.

**Enforcing policy.** Which tools exist, what they may touch, what needs approval, what is refused outright. The model has no authority of its own; it has exactly the authority the harness grants it.

Two properties of this loop matter more than they look:

**The result becomes context.** A tool result is not a return value the model "receives" privately. It is appended to the conversation as text, and from that point on it is indistinguishable from anything else in the window. That is the whole basis of prompt injection: content fetched by a tool sits alongside your instructions with no marker saying which is which.

**Tools cost tokens even unused.** Every tool definition — name, description, JSON schema — is serialised into every request. The API also inserts a tool-use system prompt: between 286 and 675 input tokens depending on the model, before your own definitions. A harness with forty tools declared is paying for forty tool definitions on every single call.

<ForEngineers>
The wire shape is a discriminated union in the content array. The model returns `content: [{type: "tool_use", id, name, input}]` with `stop_reason: "tool_use"`. You reply with a user message containing `{type: "tool_result", tool_use_id, content}`. Nothing about this is special-cased in the model's forward pass — it is text that the model was trained to produce in a particular structure, and the API validates against your schema.

This explains several behaviours that otherwise look like bugs:

- **A tool call in the visible text.** If the model produces the *description* of a call as prose instead of a structured block, no call happens and nothing errors. The turn succeeds and the loop silently does nothing.
- **Parallel calls.** One assistant message can contain several `tool_use` blocks. Return every corresponding `tool_result` in a *single* user message — splitting them across messages trains the model, within that conversation, to stop making parallel calls.
- **Errors are content, not exceptions.** A failed tool returns a `tool_result` with `is_error: true`. Dropping it entirely leaves the model with a call that never resolved, and it will usually retry.

The design consequence: a tool's `description` is a prompt. It is the only thing telling the model when to reach for it. Tool selection quality is prompt quality, and the most common cause of "the agent didn't use the tool" is a description that reads like API documentation rather than instruction.
</ForEngineers>

<ForLeads>
The strategic read: **the model is the commodity and the harness is the product.** Model capability is bought from a provider at a published price, and every competitor can buy the same thing next quarter. What differentiates one team's results from another's is the harness — what context it assembles, what tools it exposes, what it verifies before accepting output.

That reframes several decisions:

- **Provider lock-in is smaller than it feels**, if your harness is yours. Configuration, tool definitions, and workflows are portable; the model behind them is a setting. Teams that build directly against one vendor's proprietary agent framework give this up voluntarily.
- **The cost curve is under your control.** Token spend is driven by what the harness puts in the window on each call, not by the model's list price. A team whose harness resends forty tool definitions and an unpruned history on every turn will pay several times more than one that doesn't, on the identical model.
- **The security boundary is yours too.** The model has no authority. Whatever an AI system can reach, your harness granted it. This is good news: it means the controls are ordinary engineering controls — permissions, allowlists, sandboxes — rather than something exotic requiring a new discipline.
</ForLeads>

## Configuration, and what "custom tools" really means

Most harnesses expose the same knobs, whatever they call them: which model, what standing instructions, which tools are available, what needs approval, what files to load automatically. Learning one harness's vocabulary transfers to the others, because they are all configuring the same four things — model, context, tools, authority.

Underneath the branding, **agentic tooling** is that same small set: a loop, a tool registry, a permission model, and somewhere to keep state between turns. Products differentiate on ergonomics — how easily you add a tool, how approval is presented, how state survives a restart — not on having invented a different mechanism. Judge a new agentic tool by asking what it does about those four things, and the marketing falls away quickly.

"Custom tools" sounds like a deep integration. It is a function with a JSON schema and a good description. The engineering difficulty is never in the plumbing; it is in choosing the right granularity, writing a description the model interprets correctly, and returning results the model can act on. A tool that returns a 4,000-line JSON blob is technically working and practically useless — it has spent your context window to tell the model something it now has to search.

<Callout tone="danger" title="Don't let tool output reach an interpreter unchecked">
A tool result is text in the context window with no privilege marker. If your harness lets model output flow into a shell, an `eval`, a SQL string, or a template renderer, then instructions embedded in anything a tool fetched — a web page, an issue comment, a dependency's README — execute with your process's authority. Parse into a typed structure before use, allowlist the operations a tool can perform, and give anything untrusted a sandbox with no ambient credentials.
</Callout>
